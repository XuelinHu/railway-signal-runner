# 第一人称铁道信号巡检仿真实训平台模型与编码规划

## 1. 项目目标

本项目拟建设为“第一人称铁道信号巡检仿真实训平台”。平台面向铁道信号相关课程、实训和考核场景，支持教师在三维场景中拖拽布置铁路信号设备，保存训练场景；学生以第一人称视角进入场景，按照巡检任务对信号设备、道岔设备、轨旁箱体和线路附属设施进行检查、记录和评分。

当前阶段优先完成最小可用闭环：

1. 右侧模型库展示若干仿真模型。
2. 支持拖拽模型到三维场景。
3. 支持模型移动、旋转、删除和保存。
4. 支持从布置模式切换到第一人称巡检模式。
5. 支持至少一个巡检点的靠近、查看、操作和完成判定。

## 2. 推荐实施步骤

### 2.1 第一阶段：场景布置模式

目标是让教师可以快速搭建训练场景。

需要实现的功能：

1. 右侧模型库面板。
2. 模型分类：轨道基础、信号设备、道岔设备、轨旁设施、站场环境、巡检工具。
3. 拖拽模型到 Three.js 场景。
4. 通过射线检测将模型放置到地面或轨道旁。
5. 点击模型后显示选中状态。
6. 支持平移、旋转、缩放、删除。
7. 场景保存为 JSON。
8. 从 JSON 重新加载场景。

建议的数据结构：

```json
{
  "sceneName": "进站信号机巡检训练场景",
  "objects": [
    {
      "id": "signal-entry-001",
      "catalogKey": "entry_signal",
      "name": "进站信号机",
      "position": { "x": -80, "y": 0, "z": -60 },
      "rotation": { "x": 0, "y": 1.57, "z": 0 },
      "scale": { "x": 1, "y": 1, "z": 1 },
      "interactive": true,
      "inspectionPoint": true
    }
  ]
}
```

### 2.2 第二阶段：巡检训练模式

目标是让学生进入教师布置好的场景完成任务。

需要实现的功能：

1. 第一人称移动。
2. 鼠标控制视角。
3. 靠近设备后显示交互提示。
4. 设备检查弹窗或检查面板。
5. 巡检任务进度。
6. 漏检、误检、超时等评分逻辑。
7. 巡检结果报告。

### 2.3 第三阶段：故障与考核

目标是从展示型仿真升级为实训考核。

需要实现的功能：

1. 教师配置故障点。
2. 设备状态随机化。
3. 学生提交故障判断。
4. 按操作步骤评分。
5. 自动生成训练报告。
6. 保存训练记录。

## 3. 3D 模型生成总规范

使用腾讯混元大模型生成 3D 模型时，建议统一遵守以下规范。

### 3.1 正向通用要求

1. 模型应为低到中面数，适合 Web 端实时渲染。
2. 输出格式优先使用 GLB 或 glTF。
3. 单个模型应以真实比例建模。
4. 模型原点建议位于底部中心，方便拖拽放置。
5. 贴图应清晰，但不要过大。
6. 金属、混凝土、塑料、玻璃等材质应有区分。
7. 设备应具有铁路现场工业设备质感。
8. 关键部件应容易辨认，适合教学演示。
9. 模型命名应清晰，便于后续代码加载。
10. 可交互设备应保留明显的可检查区域，例如箱门、信号灯、按钮、铭牌、连杆。

### 3.2 负向通用要求

1. 不要生成卡通、玩具、科幻或游戏幻想风格。
2. 不要出现不符合铁路现场逻辑的结构。
3. 不要让设备悬空、穿模或比例严重失真。
4. 不要把信号灯、道岔、箱体、电缆等设备混合成无法识别的形态。
5. 不要出现多余人物、车辆、动物、广告牌或无关建筑。
6. 不要生成无法落地摆放的斜底模型。
7. 不要出现过度破损、爆炸、火焰、血迹等不适合教学基础场景的元素。
8. 不要生成过多细碎零件，避免 Web 端渲染压力过大。
9. 不要使用明显错误的文字标识或乱码大字。
10. 不要让模型带有版权品牌、真实铁路局标识或商业商标。

## 4. 第一批核心模型清单

### 4.1 直线铁路轨道基础段

用途：作为场景基础，支持布置其他信号设备。

正向提示词方向：

- 中国铁路线路场景。
- 直线钢轨、混凝土枕木、道砟。
- 标准轨距视觉效果。
- 模块化轨道段，可连续拼接。
- 真实工业材质，适合 Web 端低中面数模型。

负向提示词方向：

- 不要生成玩具火车轨道。
- 不要生成悬空轨道。
- 不要让左右钢轨宽度不一致。
- 不要出现夸张弯曲或断裂。
- 不要加入列车、人物或站台。

### 4.2 弯道铁路轨道段

用途：扩展线路形态，支持更真实的训练场景。

正向提示词方向：

- 平缓弯道钢轨。
- 枕木沿弯道自然排列。
- 道砟连续铺设。
- 可与直线轨道段拼接。
- 低中面数、真实比例。

负向提示词方向：

- 不要出现急转弯或过山车式轨道。
- 不要让枕木方向混乱。
- 不要让钢轨断开。
- 不要生成城市道路或地铁站台风格。

### 4.3 进站信号机

用途：核心巡检对象，用于训练信号机外观、灯位、基础和编号检查。

正向提示词方向：

- 中国铁路风格高柱进站信号机。
- 红、黄、绿信号灯位。
- 黑色信号灯头、遮檐、金属立柱。
- 基础底座、检修梯或检修平台。
- 设备铭牌和编号牌位置清晰。
- 适合轨道旁放置。

负向提示词方向：

- 不要生成交通红绿灯。
- 不要生成城市路口信号灯。
- 不要把灯位排列成不符合铁路信号机的形态。
- 不要缺少立柱或底座。
- 不要出现夸张霓虹灯、广告灯箱或装饰灯。

### 4.4 出站信号机

用途：训练出站信号设备识别和巡检。

正向提示词方向：

- 铁路出站信号机。
- 高柱结构或矮型结构可选。
- 多灯位信号机构。
- 清晰编号牌。
- 金属结构、室外设备质感。

负向提示词方向：

- 不要与公路交通灯混淆。
- 不要生成不稳定或倾斜的杆体。
- 不要加入无关电子屏幕。
- 不要让灯头数量过多导致识别混乱。

### 4.5 调车信号机 / 矮柱信号机

用途：训练学生识别小型轨旁信号设备。

正向提示词方向：

- 铁路矮柱调车信号机。
- 小型黑色信号机构。
- 低矮金属立柱。
- 底座固定在轨旁地面。
- 灯位清晰，结构紧凑。

负向提示词方向：

- 不要生成高大交通灯。
- 不要把设备做成路灯或监控摄像头。
- 不要缺少底座。
- 不要出现不必要的屏幕、按钮或广告。

### 4.6 道岔

用途：核心线路设备，用于道岔巡检、转辙机联动和故障训练。

正向提示词方向：

- 铁路道岔结构。
- 包含尖轨、基本轨、辙叉区域。
- 枕木、道砟和连接件可见。
- 轨道分叉结构明确。
- 与转辙机模型可组合使用。

负向提示词方向：

- 不要生成普通道路分叉。
- 不要让轨道分叉逻辑错误。
- 不要让尖轨位置混乱。
- 不要出现无法连接的断轨。
- 不要把道岔做成科幻机械结构。

### 4.7 转辙机

用途：重点巡检设备，用于训练转辙机外观检查、连杆检查和状态判断。

正向提示词方向：

- 铁路轨旁电动转辙机。
- 金属箱体、检修盖、固定螺栓。
- 与道岔尖轨连接的动作杆、表示杆。
- 室外工业设备质感。
- 可作为独立可交互巡检模型。

负向提示词方向：

- 不要生成普通电箱。
- 不要缺少连杆结构。
- 不要让转辙机远离道岔。
- 不要出现复杂机械臂或机器人结构。
- 不要出现透明外壳或科幻发光材质。

### 4.8 信号设备箱

用途：轨旁常见设备，用于训练箱体、门锁、编号、线缆入口检查。

正向提示词方向：

- 铁路轨旁信号设备箱。
- 金属柜体、柜门、门锁、铰链。
- 设备编号牌。
- 下方电缆入口或基础底座。
- 室外老化但整洁的工业材质。

负向提示词方向：

- 不要生成家用配电箱。
- 不要生成快递柜、储物柜或自动售货机。
- 不要让柜门比例异常。
- 不要加入不相关文字和品牌标志。
- 不要生成室内机柜风格。

### 4.9 轨道电路设备箱

用途：用于扩展信号专业设备巡检内容。

正向提示词方向：

- 轨旁轨道电路设备箱。
- 小型金属箱体。
- 电缆接口、固定底座、编号标识。
- 靠近轨道布置。
- 可与电缆槽组合。

负向提示词方向：

- 不要生成大型控制室机柜。
- 不要生成民用电表箱。
- 不要让箱体过于破败。
- 不要出现裸露危险电弧。

### 4.10 电缆槽 / 电缆沟

用途：作为轨旁附属设施，提高线路环境真实感。

正向提示词方向：

- 混凝土铁路电缆槽。
- 长条模块化结构。
- 沿轨道方向铺设。
- 可见盖板分段。
- 适合重复拼接。

负向提示词方向：

- 不要生成城市排水沟。
- 不要生成开放式深沟。
- 不要让电缆槽过宽或过高。
- 不要加入杂乱裸线。

### 4.11 应答器 / 地面信标

用途：用于扩展列控系统相关训练。

正向提示词方向：

- 铁路地面应答器。
- 安装在两根钢轨之间。
- 小型黄色或灰色设备。
- 固定螺栓和底座清晰。
- 低矮、可识别。

负向提示词方向：

- 不要生成路面减速带。
- 不要生成传感器塔或摄像头。
- 不要让设备比钢轨还高很多。
- 不要离开轨道中心区域。

### 4.12 轨旁警示牌

用途：用于场景标识和安全教育。

正向提示词方向：

- 铁路轨旁警示牌。
- 金属立柱、矩形或三角形警示牌。
- 简洁醒目的安全标识。
- 可放置在线路旁。

负向提示词方向：

- 不要使用真实公司商标。
- 不要生成商业广告牌。
- 不要加入大段乱码文字。

用途：增强线路真实感，也可作为定位训练辅助。

## 7. 物理与交互逻辑开源框架建议

当前项目已经使用 Vue、Three.js 和 Cesium。后续拖拽、碰撞和第一人称训练可按复杂度选择以下开源框架。

### 7.1 Three.js

用途：

- 三维场景渲染。
- GLB 模型加载。
- 射线检测。
- 第一人称相机。
- 模型选中、拖拽、旋转。

适合当前项目，建议继续作为核心渲染框架。

### 7.2 three-mesh-bvh

用途：

- 加速复杂模型的射线检测。
- 提升拖拽放置、点击选中、地面拾取性能。
- 适合模型数量逐渐增多后的编辑器模式。

适用场景：

- 模型库增多。
- 场景变大。
- 点击和拖拽出现卡顿。

### 7.3 cannon-es

用途：

- 轻量级 JavaScript 物理引擎。
- 支持刚体、碰撞体、重力、地面碰撞。
- 可用于第一人称角色碰撞和简单物理阻挡。

适用场景：

- 学生不能穿过设备箱、信号机、围栏。
- 角色需要受地形或地面约束。
- 简单物体碰撞即可，不追求大型物理仿真。

### 7.4 Rapier

用途：

- 高性能物理引擎。
- 支持 3D 碰撞、刚体和角色控制。
- 性能通常强于传统纯 JavaScript 物理库。

适用场景：

- 后续需要更稳定的角色控制器。
- 场景内碰撞体较多。
- 需要更可靠的 Web 端物理模拟。

### 7.5 Yuka

用途：

- 游戏 AI 和导航逻辑。
- 可用于 NPC 巡检员、引导员或自动路线演示。

适用场景：

- 后续添加教学引导角色。
- 自动演示标准巡检路线。
- 模拟其他工作人员移动。

### 7.6 Tween.js / GSAP

用途：

- 平滑动画。
- 设备箱门打开。
- 检查面板弹出。
- 相机过渡。

适用场景：

- 需要提升交互体验。
- 设备操作需要动画反馈。

### 7.7 Pinia

用途：

- Vue 全局状态管理。
- 保存当前模式、模型库、场景对象、巡检任务、评分状态。

适用场景：

- 项目从单页面小游戏扩展为平台。
- 编辑器、训练、报告多个模块共享状态。

## 8. 推荐技术选型

当前阶段建议优先级如下：

1. Three.js：继续使用，作为核心三维渲染。
2. GLTFLoader：继续使用，用于加载混元生成的 GLB 模型。
3. Raycaster：先用 Three.js 内置射线检测实现拖拽和选中。
4. cannon-es 或 Rapier：第二阶段加入，用于角色碰撞和物理阻挡。
5. Pinia：当状态复杂后加入，用于管理编辑器和训练流程。
6. three-mesh-bvh：模型变多后再加入，用于性能优化。

不建议一开始就引入太多库。第一版可以只使用 Three.js 原生能力完成拖拽布置。

## 9. 编码模块拆分建议

### 9.1 模型目录模块

建议文件：

```text
src/game/modelCatalog.js
```

职责：

- 定义右侧模型库。
- 维护模型路径、名称、分类、缩略图。
- 标记模型是否可交互、是否可作为巡检点。

### 9.2 场景编辑器模块

建议文件：

```text
src/game/sceneEditor.js
```

职责：

- 处理拖拽放置。
- 处理模型选中。
- 处理移动、旋转、删除。
- 处理吸附逻辑。
- 输出场景 JSON。

### 9.3 场景存档模块

建议文件：

```text
src/game/sceneSerializer.js
```

职责：

- 将场景对象转换为 JSON。
- 从 JSON 恢复场景。
- 校验模型 catalogKey 是否存在。
- 兼容后续版本升级。

### 9.4 巡检任务模块

建议文件：

```text
src/game/inspectionTask.js
```

职责：

- 定义巡检任务。
- 计算学生靠近设备的距离。
- 判断是否可交互。
- 记录完成状态。
- 输出评分结果。

### 9.5 物理碰撞模块

建议文件：

```text
src/game/physicsWorld.js
```

职责：

- 初始化物理世界。
- 为地面、设备、围栏创建碰撞体。
- 控制第一人称角色不能穿模。
- 同步物理对象与 Three.js 对象。

### 9.6 Vue 页面组件

建议文件：

```text
src/components/RailwaySceneEditor.vue
src/components/ModelLibraryPanel.vue
src/components/InspectionTaskPanel.vue
src/components/SceneObjectInspector.vue
```

职责：

- `RailwaySceneEditor.vue`：三维编辑主界面。
- `ModelLibraryPanel.vue`：右侧模型库。
- `InspectionTaskPanel.vue`：巡检任务面板。
- `SceneObjectInspector.vue`：选中模型的属性编辑面板。

## 10. 后续编码顺序

建议按以下顺序推进：

1. 新增 `modelCatalog.js`，先配置 3 个模型：进站信号机、转辙机、信号设备箱。
2. 新增右侧模型库面板，先用假缩略图或文字卡片展示。
3. 实现点击模型卡片后，在场景中心生成模型。
4. 再升级为拖拽到场景指定位置生成。
5. 实现选中模型后的移动、旋转、删除。
6. 实现场景 JSON 保存和加载。
7. 将保存后的场景切换到第一人称巡检模式。
8. 对可交互模型添加巡检任务。
9. 加入碰撞逻辑，防止学生穿过设备。
10. 加入评分和报告。

## 11. 第一版最小模型集

第一版不建议一次生成 20 个模型。建议先生成以下 5 个：

1. `rail_straight.glb`：直线轨道。
2. `entry_signal.glb`：进站信号机。
3. `switch_machine.glb`：转辙机。
4. `signal_equipment_box.glb`：信号设备箱。
5. `cable_trough.glb`：电缆槽。

这 5 个模型足以完成一个可演示闭环：

1. 教师布置轨道和设备。
2. 学生进入第一人称场景。
3. 学生靠近进站信号机、转辙机和设备箱。
4. 系统记录巡检进度。
5. 生成简单训练结果。
